# Visual Attachment Findings — What Actually Renders

*Prepared by the visual-attachment-designer agent. Read-only audit: no production code was modified.*
*Evidence: full static read of `src/linkedin_visuals.py`, `src/linkedin_diagrams.py`, `src/autonomous_visual_engine.py`, the LinkedIn call sites in `src/scheduler.py` (`AutomaterEngine._execute_linkedin_post`), plus `src/linkedin_automater.py`, `src/linkedin_portfolio_manager.py`, `src/ai_generator.py`, `src/growth.py`, `tests/test_linkedin_visuals.py`. One pre-generated artifact (`generated_visuals/linkedin/test_flow/test_flow_first_frame.png`) was opened and visually inspected. Python is not installed in this environment, so no new render was executed; conclusions about the carousel cover are from the renderer source.*

---

## Verdict up front

1. **The "animated" LinkedIn attachment is almost never animated.** `LINKEDIN_PREFER_STATIC_VISUALS` defaults to `"true"` in `scheduler.py:1967`, so the flow format attaches the **first frame PNG** of a 40-frame GIF. That first frame is the *worst* frame: metric bars are at 0% fill and no component is marked active. It is decoration, not information. This is the single biggest engagement defect.
2. **The AI-written alt text is dead code.** `render_linkedin_carousel()` returns `alt_text` (`linkedin_visuals.py:851`), but `_execute_linkedin_post` never reads it. LinkedIn PDF posts get a *document title* (cover headline), and image posts get `altText` = topic title. There is no descriptive alt text on any attachment.
3. **The auto-visual engine is unreachable.** `autonomous_visual_engine.py` advertises MP4/GIF/casual cards, but no production module imports it. No MP4 is ever attached by this codebase.

**Plain answer on text-only:** for the `animated_flow_gif` path, **yes — text-only currently beats the attachment**. For the `notebook_carousel` path, text-only wins only until the carousel actually ships reliably; the study-note PDF is the one asset with real save value, but two gates suppress it far more often than intended.

## 2. What slide 1 actually looks like

`_cover_slide()` (`linkedin_visuals.py:258-331`) renders an 1080 × 1350 warm-ivory notebook page:

- 50 px drafting graph grid, soft-red vertical margin line at x=68.
- Stamp at y≈84: `// ARCHITECTURAL STUDY NOTES` (16 px tracked, terracotta).
- Kicker at y≈152: `// FIELD REPORT · {kicker or category or "SYSTEMS DESIGN"}` (20 px, navy).
- Double rule at y=196/202.
- **Headline:** serif bold, auto-fitted 76 → 52 px, max 3 lines, from `headline`/`title`, default `"Engineering Field Notes"`. Starts at y=236.
- **Subhead:** 30 px sans, ≤3 lines, graphite.
- **Learning objectives card** if `objectives`/`learning_objectives` exists (the educational-plan schema does provide these): white card, navy left bar, label `// IN THIS STUDY NOTE · LEARNING OBJECTIVES`, up to 4 numbered bullets at 25 px. The comparison plan does not supply objectives, so it falls back to a terracotta-bar card labelled `📌 ENGINEERING CONTEXT & PRODUCTION REALITY` with a 5-line generic paragraph about "memory, latency, and operational boundaries" — **generic filler that varies little by topic**.
- **Swipe bar** at y≈1140: `SWIPE THROUGH THE {total}-PAGE STUDY NOTES` (20 px tracked, navy) and a literal `-->` arrow at the right.
- **Footer:** rule at y=1238, `ARCHITECTURE NOTEBOOK` (18 px tracked, navy) at x=92 and `PAGE 01 / 0N` (18 px, slate) right-aligned, both at y=1266.

**Legibility:** the headline (52–76 px) and subhead (30 px) survive 320 px rendering. The objectives (25 px) and all metadata/kicker/footer text (13–20 px) do not — at 320 px they are ~4–6 px tall. This is acceptable for a footer, not for body content.

**Subsequent slides** (`_point_slide`, `_comparison_slide`, `_diagram_slide`, `_code_slide`, `_pitfalls_slide`, `_framework_slide`, `_cta_slide`): body text is 21–26 px; code is 17–21 px mono; detail text is 14–21 px. At 320 px these are effectively unreadable. The technical content exists but cannot be read in-feed — it only works if the viewer opens the PDF, which is a much higher-commitment action than a swipe.

The editorial flow frame (inspected artifact) is cleaner: dark header block, large serif title, three named sections, white cards. Its supporting text is 10–15 px, also too small at feed scale.

## 3. Brand / URL / "recent change" verification

The requested changes are **present in the code and actually render clean**:

- **Website pill:** `_cta_slide()` only draws the pill when `cta["website"]` is non-empty (`linkedin_visuals.py:760-765`). The generator prompt says *"Keep the website field empty"* (`ai_generator.py:565`), the schema defaults it to `""` (`:548`), and `_normalize_carousel_plan` defaults to `""` (`:632`). `sanitize_plan()` (`growth.py:81`) additionally strips URLs from every string in the plan before rendering. **No URL renders on the CTA slide in the normal path.** The pill is still reachable if Gemini ignores the instruction, because the renderer trusts the field — it is a latent risk, not a current default.
- **Footers:** carousel footer now renders the neutral descriptor `ARCHITECTURE NOTEBOOK` + `PAGE NN / NN` (`:231-238`), not a brand name. Diagram footers render `ENGINEERING NOTES` / `ENGINEERING BLUEPRINTS` (`linkedin_diagrams.py:377-383`); editorial frames render `Systems Architecture Series` / `Save this` (`:743-745`). No brand, no URL, no handle anywhere on the visuals.
- **Other stamp text** (`// FIELD REPORT`, `// ARCHITECTURAL STUDY NOTES`, `// IN THIS STUDY NOTE · LEARNING OBJECTIVES`, `// THE GOLDEN RULE OF THUMB`) is neutral editorial scaffolding.

**Remaining non-brand but decorative filler:** emoji glyphs `📌` (`linkedin_visuals.py:317`), `💡` (`:475`), `⚡/🌿/💬/🔁` in `autonomous_visual_engine.py`, plus `· Save this.` appended to the editorial subtitle (`linkedin_diagrams.py:563`). `get_font()` loads Segoe UI / Arial / DejaVu files, not an emoji font, so these are likely tofu boxes rather than glyphs on some systems. They are decoration, not signal, and should be removed.

## 4. Bugs and quality defects

**B1 — PDF→hero fallback is dead.** `linkedin_automater.post()` retries a failed document upload or a 4xx document post using `{base}_hero.png` (`linkedin_automater.py:412-415`, `:476-484`). `render_linkedin_carousel()` never writes that file; `render_linkedin_hero()` is never called by the scheduler. Net effect: a LinkedIn document API hiccup drops the attachment entirely instead of degrading to the cover image.

**B2 — The default static frame is the empty-data frame.** `render_editorial_architecture_gif()` saves `images[0]` as the preview PNG (`linkedin_diagrams.py:776-778`). At `progress=0`: `ease = min(1.0, progress*1.4) = 0`, so all metric bars have `fill_w = 0` (`:698-703`), and `card_highlight` requires `progress >= 0.40` (`:623`), so no component shows an ACTIVE score. Verified in the inspected artifact: three empty progress tracks and no active expert. The scheduler attaches exactly this PNG by default.

**B3 — Alt text is generated then discarded.** `render_linkedin_carousel()` returns `alt_text` from the plan (`linkedin_visuals.py:851`, generated ≤180 chars at `ai_generator.py:655`), but `_execute_linkedin_post` ignores it and uses the headline as `media_title` instead (`scheduler.py:1941`, `:2050`). Document posts carry `title` only (`linkedin_automater.py:461`), so carousels have **no alt text at all**; GIF/PNG posts get the bare topic title as `altText`. This loses the one descriptive accessibility/context field we already pay Gemini to write.

**B4 — Topic-affinity validator can suppress valid carousels.** `validate_topic_attachment()` (`scheduler.py:165-205`) requires ≥2 significant title words (when the title has >2) to appear in the media path. Carousel paths are built from the *creative cover headline* slug (`linkedin_visuals.py:818-822`), not the topic title. A headline like "The Quiet Cost of Copying Bytes" for a topic about serialization can fail the check and be set to `None` at `scheduler.py:2034-2040`. The same risk applies to the GIF path, where `base_name` comes from the spec title.

**B5 — The standard "professional carousel" plan has no `pages`, so it is always suppressed.** The scheduler only renders when `carousel_plan["pages"]` exists and has ≥4 entries (`scheduler.py:1935`). `generate_linkedin_carousel_plan()` builds a legacy `cover`/`slides`/`framework`/`cta` plan (`ai_generator.py:584-660`) and copies `pages` only if Gemini happens to return it (`:658-659`) — the prompt never asks for `pages`. The plan renderer itself supports the legacy schema (`linkedin_visuals.py:781-790`), so the gate is stricter than the producer. Effect: the generic "LinkedIn Topic (Professional Carousel)" branch (`scheduler.py:1859-1869`) effectively never produces an attachment.

**B6 — Long body text can be covered by the sticky note.** `_point_slide()` allows up to 18–22 body lines (`:380-381`) but clamps the takeaway box top to ≤980 (`:385-386`). With a dense body, the last lines extend past y≈1000 and the canary box is drawn over them (`:391-396`). Bodies are usually ≤240 chars from the generator, so this is latent rather than constant.

**B7 — Dead code with misleading contract.** `autonomous_visual_engine.py`'s module docstring claims MP4/GIF output (`:9`), but the module has no callers; `compile_frames_to_mp4()` (`:182`) is only reachable from `render_dynamic_concept_comparison()` (`:495`), which nothing invokes. No MP4 is attached anywhere.

## 5. Concrete engagement-focused attachment spec

Design target: a technical creator feed where the attachment must earn a **save** or a **swipe-stop**, not a like.

**Format choice**
- Default to **text-only** unless the visual carries information the caption cannot. The portfolio's own `decide_portfolio_format()` already does this for opinion/analysis (`linkedin_portfolio_manager.py:103-106`); keep it.
- Carousel (PDF, 1080 × 1350) only for genuinely sequential content: checklist, internals walkthrough, comparison matrix, failure modes.
- Static PNG only for a single diagram that is readable at a glance. A looping GIF adds nothing semantically and is downgraded to a static PNG anyway — prefer generating the PNG directly and skip the 40-frame render cost.
- Never attach MP4 here; LinkedIn document/image posts are the target.

**Slide 1 must say (in order)**
1. A **specific claim with a number or named subject**, not a topic label. Bad: "Event Streaming Architecture". Good: "Kafka holds 3 days of history. RabbitMQ deletes after ack."
2. One line of **consequence for the reader** ("Your replay story changes at this boundary").
3. A **concrete payoff list** of 3 items (the actual questions the deck answers), no generic learning objectives.
4. The swipe cue as a **benefit**, not an instruction: "3 decisions this changes" rather than "SWIPE THROUGH THE 6-PAGE STUDY NOTES".
5. No emoji, no masthead, no page chrome beyond a small `01 / 06`.

**Slides 2..N**
- 5–7 slides total. Slide count is set by content, not by a template.
- **One idea per slide.** Headline + 1 diagram/table + 1 takeaway line. Information density high in *specificity*, low in *word count*: ≤60 words of body per slide.
- **Text sizes on the 1080 × 1350 canvas:** headline 64–84 px; slide title 44–56 px; body 30–36 px; labels/captions ≥26 px; footer ≥20 px. Nothing below 26 px carries meaning. At 320 px display this yields 8–11 px body text, which is the floor for legibility.
- **Contrast:** existing ivory/charcoal palette is strong (INK `#181C24` on PAPER `#FCF9F2`, ratio ≈ 15:1). Keep it. Accent colors are for one emphasis per slide, never decorative.
- **Diagram slides:** every arrow/stage must be labelled with the *payload* moving, not just "Stage 2". An unlabelled box is decoration.
- **Code slides:** ≤14 visible lines at 26+ px mono; crop to the 5 lines that matter instead of shrinking to 17 px.

**Footer policy**
- Neutral descriptor + page number only (`ARCHITECTURE NOTEBOOK · 02/06` is acceptable). No brand, no URL, no handle, no "Follow for more", no "Save this" instruction — the content should earn the save.
- Remove `· Save this.` from the editorial subtitle and the `Save this` footer item. Begging for saves is a weak substitute for a useful visual.

**Website pill**
- **Do not render one.** Keep `website` empty in the schema and delete the rendering branch in `_cta_slide()` rather than relying on the generator prompt to keep it empty.

**What makes it save-worthy**
- A number, a threshold, or a decision rule the reader can reuse in their own system ("p99 budget is dominated by the disk flush; measure that first").
- A comparison table with *named* trade-offs, not "Option A / Option B".
- A failure mode with impact and fix, stated in one line each.
- If a slide cannot state a reusable fact, delete the slide.

**Verification rule**
- Open the attachment at **320 px width** before publishing. If any text that carries meaning is unreadable, the slide fails.

## 6. Three cheapest high-impact code changes

All are small, local, and leave production code untouched in this audit.

### Change 1 — `render_editorial_architecture_gif` (`src/linkedin_diagrams.py:750-799`)
Make the preview PNG a **mid-loop, data-complete frame** instead of frame 0. In the preview-save block (`:776-778`), save `images[frames // 2]` (progress ≈ 0.5) as `_first_frame.png`; leave the GIF frame loop unchanged.
*Impact:* the default LinkedIn attachment (static PNG, per `scheduler.py:1969-1971`) then shows filled metric bars, an ACTIVE expert card, and the highlighted step. This converts the most common attachment from decoration to information at the cost of one index change.

### Change 2 — `render_linkedin_carousel` (`src/linkedin_visuals.py:816-852`)
After saving the per-slide PNGs, also save slide 1 as `folder / f"{base}_hero.png"`. Optionally include that path in the returned dict.
*Impact:* revives both dead fallbacks in `linkedin_automater.post()` (`:412-415` and `:476-484`), so a document-upload failure degrades to the cover image instead of dropping the attachment. One `image.save(...)` line; no new renderer.

### Change 3 — `validate_topic_attachment` (`src/scheduler.py:165-205`)
Align the affinity check with the actual artifact naming: accept a match against the **cover headline slug** as well as the topic title, and drop the `required = 2` rule for carousels/filenames derived from generated creative text (`:198-203`). Cleanest variant: add an optional `extra_tokens` argument and pass `carousel_plan["cover"]["headline"]` from `AutomaterEngine._execute_linkedin_post` (`:2035`).
*Impact:* stops valid, topic-correct carousels from being silently downgraded to text-only. Pair this with removing the `pages` gate at `:1935` (or normalizing the legacy plan into `pages` in `AIGenerator._normalize_carousel_plan`, `ai_generator.py:584`), otherwise the professional-carousel branch still never renders — treat that normalization as the immediate follow-up, not a fourth change.

**Near-free fourth (not in the top 3):** pass `assets["alt_text"]` into `media_title` or a new `alt_text` argument at `scheduler.py:1938-1941` / `:2050`, fixing B3 and giving image posts a real description.

## 7. Does an attachment hurt reach? (plain statement)

**Yes, for `animated_flow_gif` — publish text-only.** The attached PNG is a first frame with empty bars, its body text is 10–15 px on a 1080 px canvas (unreadable at 320 px), and the "animation" that justified the format is suppressed by default. It adds no claim the caption does not already make. A crisp 1,000-character technical article with one concrete rule outperforms this image; the image also signals low-effort automation on a creator account.

**For `notebook_carousel` — keep it, but only after Changes 2 and 3.** The PDF is the one format with genuine save value (reusable rules, failure modes, a decision matrix), and the notebook aesthetic is distinct from generic AI-slop carousels. Today it is suppressed by the `pages` gate and the affinity validator often enough that its real-world contribution is smaller than its design potential.

**Caveat:** there is no engagement-outcome telemetry in `data/` (`engagement_queue.json` is a work queue, not results), so this is a design judgment, not a measured A/B result. The cheapest way to settle it is to log `visual_format` against saves/comments per post for 20 posts after applying Change 1.
